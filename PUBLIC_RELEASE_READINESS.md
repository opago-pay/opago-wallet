## HashPack first-deposit incompatibility — 17 September 2026

A newly generated Opago wallet has an Ed25519 public key before any Hedera account exists. The SDK key alias `0.0.<DER public key>` is valid for an SDK alias transfer, but it is not a numeric account ID. HashPack web v14.4.1 rejects that 92-character value with `Unknown account format`; it also rejects the same Ed25519 public key in raw (64 characters) and DER (88 characters) form. Removing `0.0.` does not solve the compatibility issue. Its public recipient validator accepts an ECDSA DER key and numeric account IDs. This was reproduced offline against the exact public `checkAccountExists` method with dialogs/network stubbed, not by submitting a payment. Local evidence: `.codex-local-evidence/hashpack-format-reproduction.json`. A read-only Mainnet public-key lookup found no account for the reported wallet at investigation time; the user’s key is omitted from versioned evidence.

The receive-screen source now shows a clear activation requirement and copyable public-key details instead of presenting the incompatible alias as a payment QR. Existing activated accounts retain their numeric QR. This UI correction is not an activation service and has not yet been installed on the devices. The product decision and funding for one-time native Hedera account creation remain pending. No private key, recovery phrase, funded account creation or payment was used during this investigation.

Ordinary Opago HBAR payments already use `TransferTransaction` directly. The deployed contract is an optional, separate merchant-checkout path, unrelated to first-account activation. Native `AccountCreateTransaction` or a supported alias transfer can establish the first numeric account; neither requires a smart contract. Preserve the existing recovery derivation when adding account activation rather than silently changing existing wallets from Ed25519 to ECDSA.

The owner raised cost concerns and has not approved an Opago-funded activation service. The current Hedera fee table lists a standard CryptoCreate base fee of USD 0.05 (https://docs.hedera.com/networks/fees), with transaction-specific extras possible. Hedera alias auto-creation can instead charge the transfer payer (https://hedera.com/blog/how-to-auto-create-hedera-accounts-with-hbar-and-token-transfers/). A sender-funded first deposit using HashPack-supported ECDSA addressing is a design option for future wallets, not implemented or accepted for the existing Ed25519 derivation. Existing wallets must not silently change keys/account identity. No funding or activation transaction has been executed. The prepared receive UI passes TypeScript, ESLint and all 170 application tests; it remains uninstalled while the activation path is being decided.
