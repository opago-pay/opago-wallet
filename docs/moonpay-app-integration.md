# MoonPay buy integration (app side)

The native Buy screen is available from Home. Bitcoin is the default asset; HBAR stays under Advanced options. It uses `@moonpay/react-native-moonpay-sdk` 1.1.8 with `expo-web-browser` (Android Custom Tabs / iOS Safari View Controller). The React Native WebView dependency is installed because the SDK declares it as a peer dependency, but Opago opens the in-app browser variant.

Set `EXPO_PUBLIC_MOONPAY_BACKEND_URL` to the HTTPS origin of Opago's MoonPay backend. The production-candidate script accepts the same public URL through `-MoonPayBackendUrl`; without that option its build deliberately leaves buying unavailable. This URL is public build metadata, never a secret. Without a configured and reachable backend, Buy shows “Buying is not available yet” and cannot launch checkout. No production key or API secret belongs in the app.

The separate backend must implement:

- `GET /api/moonpay/config` → `{enabled:true,environment:"sandbox"|"production",publicApiKey,assets:[{asset:"BTC",network:"bitcoin",moonpayCurrencyCode:"btc"},{asset:"HBAR",network:"hedera",moonpayCurrencyCode:"hbar"}],fiatCurrencies:["EUR"],redirectUrl:"https://..."}`. It may return `{enabled:false,reason:"not_configured"}`. The app rejects unrecognized asset/network/code pairs, invalid redirects, environment/key mismatches, and non-EUR configurations.
- `POST /api/moonpay/sign-checkout` with JSON `{unsignedUrl}` containing the **exact URL generated by the SDK for the in-app browser variant**, and return `{signature}` containing the raw Base64 HMAC signature. Sign only after validating the asset, environment, amount, wallet destination and all allowed query parameters server-side. Keep the MoonPay secret on the backend. Use the existing backend authentication policy; the app does not require a new login.

For backend failures, return `{error:{code,message}}` with a safe message and one of `MOONPAY_NOT_CONFIGURED`, `INVALID_CHECKOUT`, `UNSUPPORTED_ASSET`, `NETWORK_MISMATCH`, or `RATE_LIMITED`. The app shows a generic retry message without displaying the signed URL, address, or backend internals.

The app requests a reusable Spark Bitcoin Mainnet deposit address, validates it, and enables the existing deposit watcher before launching BTC checkout. BTC purchase deposits can still need Bitcoin confirmation and a user-approved claim fee before becoming available. For HBAR, the app resolves a real Hedera Mainnet account from the wallet's own public key via the mirror node; an inactive account blocks checkout. It does not use an alias or memo.

For every tap the app creates one immutable SDK instance for the selected asset, integer EUR amount and destination. It signs the generated URL, checks the signed browser URL preserves those parameters, and launches the browser once. Editing a field or switching wallets discards the old instance. Browser return is only a neutral status: it does not create a transaction, modify balances or claim purchase success. Returning to Home triggers the existing balance/deposit refresh.

Before production release, the backend owner must verify MoonPay-supported BTC/HBAR currency codes and wallet address formats for this integration, configure the approved HTTPS redirect and any MoonPay go-live parameters, and test signing in sandbox. Opago's team must test the resulting Android/iOS browser flow, cancellation, resume after the wallet locks, deposit detection/claim and HBAR credit with provider test transactions. No real purchase was made during implementation.
